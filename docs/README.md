# ai-project-kit 项目实施指导手册

本文档以 `docs/demo/` 中的「中学教务管理系统」为案例，说明如何使用 `ai-project-kit` 从需求收集推进到交付验收，并在每个阶段明确：前置条件、角色职责、主要动作、输入产物、输出产物、量化标准、AI-Agent 参与方式、人工确认点，以及项目过程中应该如何持续优化和沉淀。

`docs/demo/` 是按 `ai-project-kit` 初始化出来的完整示例项目，内部结构应保持和真实项目一致：

```text
docs/demo/
├── README.md
├── 01_req/
├── 02_build/
├── 03_qa/
├── 04_change/
├── 05_delivery/
├── 06_gov/
├── cursor-script/
└── qoder-script/
```

其中 `docs/demo/README.md` 是 Demo 项目自己的入口说明，和六大工作组平级；本文件是 `docs` 级别的实施指导手册。

## 1. 案例背景

本案例模拟一个中学内部使用的教务管理系统，主要功能包括：

- 登录。
- 主页。
- 学生管理。
- 班级管理。
- 教师管理。
- 学生课程管理。
- 学生成绩管理。

本案例刻意控制范围，不包含排课算法、在线选课、家长端、复杂统计分析和第三方系统集成。这样做的目的不是弱化项目真实性，而是让使用者能清楚看到完整的阶段衔接链路。

## 2. 总体工作机制

`ai-project-kit` 把项目资产拆分为六大工作组：

| 工作组 | 目录 | 主要职责 |
|--------|------|----------|
| 需求组 | `demo/01_req/` | 需求输入、原型、需求基线 |
| 实施组 | `demo/02_build/` | 架构、详细设计、数据库、编码、发布 |
| 测试组 | `demo/03_qa/` | 测试验证、质量报告 |
| 变更管理组 | `demo/04_change/` | 缺陷与正式变更登记、影响分析 |
| 交付组 | `demo/05_delivery/` | 验收、交付包、用户手册、培训、运维交接 |
| AI 治理组 | `demo/06_gov/` | AI 使用留痕、输出验收、安全检查、复盘 |

推荐执行链路：

```text
需求输入
  -> 需求分析
  -> 可运行原型
  -> 需求基线
  -> 架构设计
  -> 软件功能说明
  -> 数据库设计
  -> 编码实现
  -> 测试与质量报告
  -> 变更登记与闭环
  -> 版本发布
  -> 交付验收
  -> AI 治理复盘
```

## 3. 阶段 1：需求输入与调研

目录：`demo/01_req/workspace/01_inputs/`

案例产物：`interview-notes.md`

### 前置条件

- 已明确项目背景和业务目标。
- 已确定访谈对象，例如教务主任、年级组长、任课教师、信息管理员。
- 已收集现有 Excel、纸质流程、历史问题或系统截图。

### 角色职责

| 角色 | 职责 |
|------|------|
| 业务分析人员 | 组织访谈、记录业务事实、识别待确认问题 |
| 业务负责人 | 说明真实业务流程和痛点 |
| AI-Agent | 从访谈纪要中提取候选需求、角色、约束和问题 |

### 主要动作

- 访谈业务人员，记录真实流程和痛点。
- 收集现有表单、台账、系统截图和规则说明。
- 将已确认事实、待确认问题、假设分开记录。
- 使用 AI-Agent 提取候选需求和问题清单。

### 输出产物

- 访谈纪要。
- 现状流程说明。
- 输入材料清单。
- 待确认问题清单。

### 量化标准

- 核心角色访谈覆盖率达到 100%。
- 每个重要问题都记录来源和确认人。
- 待确认事项单独编号，不混入已确认结论。

### 优化与沉淀

- 把高质量访谈问题沉淀为需求阶段 Prompt。
- 把常见遗漏项沉淀到 `01_req/playbook/01_requirements/rules/`。
- 如果项目较复杂，可把访谈纪要拆为按角色、按流程或按模块分别管理。

## 4. 阶段 2：范围、角色与需求分析

目录：`demo/01_req/workspace/01_inputs/`（范围与角色分析材料与访谈纪要同层存放，案例为 `scope-and-roles.md`）

案例产物：`scope-and-roles.md`

### 前置条件

- 已完成基础访谈。
- 已有初步业务范围和模块清单。
- 已识别主要用户角色。

### 角色职责

| 角色 | 职责 |
|------|------|
| 业务分析人员 | 拆分范围、角色、业务规则和边界 |
| 业务负责人 | 确认范围内、范围外和优先级 |
| AI-Agent | 整理角色权限初稿、识别范围冲突和遗漏 |

### 主要动作

- 明确范围内功能和范围外功能。
- 定义教务管理员、班主任、任课教师、系统管理员的职责。
- 梳理关键业务规则，例如学生必须归属有效班级、成绩范围为 0-100。
- 标记会影响设计、数据库和测试的业务约束。

### 输出产物

- 范围边界说明。
- 角色权限初稿。
- 关键业务规则。
- 下游使用说明。

### 量化标准

- 范围内功能必须能映射到后续 REQ 编号。
- 每个角色至少明确可访问模块和数据范围。
- 范围外事项必须有原因，不能只写“不做”。

### 优化与变通

- 小项目可以把范围说明和需求规格放在一个文件中。
- 多角色项目建议单独维护权限矩阵，避免后续开发和测试反复确认。
- 需求仍不稳定时，不要急于进入设计，应先形成待确认问题闭环。

## 5. 阶段 3：原型设计与可运行演示

目录：`demo/01_req/workspace/02_prototypes/`

案例产物：

- `prototype-notes-v1.0.md`
- `prototype-app/`

### 前置条件

- 已明确主要模块和角色权限。
- 已有需求清单或候选需求。
- 已确定需要业务确认的关键页面和交互。

### 角色职责

| 角色 | 职责 |
|------|------|
| 业务分析人员 | 主导原型设计、组织业务确认、记录反馈 |
| 业务负责人 | 确认页面、字段、按钮和操作流程 |
| AI-Agent | 生成页面清单、字段说明和 Vue 原型初稿 |
| 后续开发人员 | 参考原型理解页面布局和交互意图 |

### 主要动作

- 产出页面清单和页面流转说明。
- 产出可运行前端原型，用于业务确认。
- 按角色展示不同菜单和操作入口。
- 记录业务反馈，并同步影响到需求基线和软件功能说明。

原型运行：

```bash
cd docs/demo/01_req/workspace/02_prototypes/prototype-app
npm start
```

默认访问：

```text
http://localhost:4173
```

### 输出产物

- 页面原型说明。
- 可运行 Vue 原型。
- 页面字段、按钮、菜单和流转说明。
- 原型确认记录。

### 量化标准

- 高优先级需求必须有对应页面或交互说明。
- 每个页面必须说明关联 REQ 编号。
- 关键字段和操作按钮必须经过业务确认。
- 业务反馈必须有处理结论：采纳、暂不采纳、进入后续迭代。

### 优化与变通

- 文档无法表达视觉效果时，应优先补可运行原型或截图。
- 原型代码是需求阶段产物，不等同于正式生产代码。
- 如果项目对 UI 要求高，可以把原型进一步拆成页面组件、交互状态和设计规范。
- 如果时间紧，可先做关键流程原型，不必覆盖所有低优先级页面。

## 6. 阶段 4：需求规格、追踪与基线

目录：`demo/01_req/workspace/03_baseline/`

案例产物：

- `requirements-spec-v1.0.md`
- `requirements-traceability-v1.0.md`
- `requirements-review-v1.0.md`
- `requirements-baseline-v1.0.md`

### 前置条件

- 输入材料、范围分析和原型说明已完成。
- 关键待确认问题已关闭，或明确不阻塞本版本。
- 业务负责人愿意对需求范围做确认。

### 角色职责

| 角色 | 职责 |
|------|------|
| 业务分析人员 | 编写需求规格、追踪矩阵和评审记录 |
| 业务负责人 | 确认需求基线 |
| 项目负责人 | 确认范围和版本边界 |
| AI-Agent | 生成需求清单、验收条件、追踪矩阵初稿 |

### 主要动作

- 给每条需求分配 REQ 编号。
- 补充验收条件、优先级、来源和负责人。
- 建立需求、原型、设计和测试之间的追踪关系。
- 组织需求评审并签发需求基线。

### 输出产物

- 需求规格说明书。
- 需求追踪矩阵。
- 需求评审记录。
- 已签发需求基线。

### 量化标准

- 需求项编号覆盖率 100%。
- 高优先级需求验收条件覆盖率 100%。
- 需求评审问题必须关闭或转为有责任人和期限的待办。
- 下游设计不得引用未基线化需求。

### 优化与变通

- 需求变化频繁时，应尽早引入变更管理，而不是反复覆盖基线。
- 小项目可以把追踪矩阵做轻量，但不能没有 REQ 编号。
- 若原型反馈影响需求，应先更新需求基线，再通知实施组引用新版本。

## 7. 阶段 5：系统架构设计

目录：`demo/02_build/workspace/01_architecture/`

案例产物：`architecture-design-v1.0.md`

### 前置条件

- 需求基线已签发。
- 原型和非功能需求已可引用。
- 技术约束、部署环境和团队能力已初步明确。

### 角色职责

| 角色 | 职责 |
|------|------|
| 架构师 | 确认系统边界、技术选型、模块划分和风险 |
| 开发负责人 | 评估实现可行性 |
| 运维或环境负责人 | 确认部署、备份、运行约束 |
| AI-Agent | 汇总架构驱动因素、生成方案对比和风险清单 |

### 主要动作

- 识别架构驱动因素，例如权限、数据一致性、性能和可维护性。
- 做技术选型和架构决策。
- 定义模块边界和数据流。
- 输出架构风险和验证方案。

### 输出产物

- 架构设计说明。
- 架构决策记录。
- 模块划分说明。
- 系统数据流说明。
- 架构风险清单。

### 量化标准

- 每个高优先级非功能需求都有架构策略。
- 每个关键技术决策都有理由和影响说明。
- 每个风险都有缓解措施或验证方式。
- 详细设计必须引用 ARCH 编号。

### 优化与变通

- Demo 或小项目可以采用单体架构，不必为了形式拆微服务。
- 架构文档不应只写技术栈，还要写取舍理由。
- 如果后续发现架构假设错误，应通过变更记录回传，而不是口头调整。

## 8. 阶段 6：详细设计与软件功能说明

目录：`demo/02_build/workspace/02_design/`

案例产物：`software-function-spec-v1.0.md`

### 前置条件

- 需求基线、原型和架构设计已完成。
- 模块边界、角色权限和数据对象已基本明确。
- 需要为 AI-Agent 生成代码准备足够具体的输入。

### 角色职责

| 角色 | 职责 |
|------|------|
| 设计负责人 | 输出软件功能说明、接口契约和权限规则 |
| 开发负责人 | 确认可实现性和分层结构 |
| 测试负责人 | 提前识别测试关注点 |
| AI-Agent | 生成模块说明、接口草稿、异常场景和测试关注点 |

### 主要动作

- 按模块编写软件功能说明。
- 明确页面字段、按钮、接口、参数、返回值、错误提示和权限规则。
- 明确异常场景、边界条件和测试关注点。
- 标注 AI 代码生成注意事项。

### 输出产物

- 软件功能说明文档。
- 接口契约。
- 权限矩阵。
- 状态或规则说明。
- 设计追踪矩阵。
- AI 代码生成注意事项。

### 量化标准

- 每个高优先级 REQ 必须有对应 DES 设计项。
- 每个可开发模块必须包含字段、接口、校验、权限和异常说明。
- 每个接口必须说明方法、路径、参数、返回和错误场景。
- 编码阶段可以直接根据本阶段产物拆任务。

### 优化与变通

- 这是连接 AI 生成代码的核心阶段，不能只写概要设计。
- 如果 AI 生成代码质量差，优先检查软件功能说明是否不够具体。
- 对 UI 复杂、权限复杂或状态复杂的功能，应单独增加状态图、权限矩阵或流程图。
- 如果项目规模小，详细设计可以按模块合并，但不能省略接口和校验规则。

## 9. 阶段 7：数据库设计

目录：`demo/02_build/workspace/03_database/`

案例产物：`database-design-v1.0.md`

### 前置条件

- 软件功能说明已明确数据对象和字段。
- 架构设计已确认使用关系型数据库。
- 关键业务规则已明确，例如学号唯一、成绩范围、学生课程关系不可重复。

### 角色职责

| 角色 | 职责 |
|------|------|
| DBA 或开发负责人 | 确认表结构、字段、索引、约束和脚本 |
| 设计负责人 | 确认数据模型与功能说明一致 |
| AI-Agent | 生成候选表结构、字段字典和 DDL 初稿 |

### 主要动作

- 设计核心表和字段。
- 定义唯一约束、索引、校验约束和初始化数据。
- 输出 DDL 片段和回滚说明。
- 将数据表映射到 REQ 和 DES。

### 输出产物

- 数据库设计说明。
- 字段字典。
- DDL 脚本或片段。
- 初始化数据说明。
- 数据校验和回滚策略。

### 量化标准

- 核心业务表字段字典完整率 100%。
- 每个唯一性规则必须有服务层校验或数据库约束。
- 成绩、状态、角色等关键字段必须有取值范围说明。
- 数据库变更必须能关联到需求或设计项。

### 优化与变通

- Demo 可只提供 DDL 片段；真实项目应拆出可执行脚本和回滚脚本。
- 数据模型不应机械照搬页面字段，要结合查询、约束、历史数据和审计要求。
- 如果数据库设计反推发现需求不合理，应回到需求或详细设计阶段修正。

## 10. 阶段 8：编码实现与 AI 代码生成

目录：`demo/02_build/workspace/04_codebase/`

案例产物：`runnable-example/`

### 前置条件

- 软件功能说明文档和开发实现计划已完成。
- 数据库设计已完成。
- 编码规范和工程结构已明确。
- 需求、设计、数据库产物均可追踪。

### 角色职责

| 角色 | 职责 |
|------|------|
| 开发人员 | 编写关键逻辑、审查 AI 代码、提交实现 |
| 开发负责人 | 拆分任务、评审代码、确认合并 |
| AI-Agent | 生成代码骨架、DTO、CRUD、单元测试初稿 |
| 测试人员 | 提前确认测试入口和已知风险 |

### 主要动作

- 读取 `demo/02_build/workspace/02_design/implementation/` 下的总入口、全局要求和模块级开发实现文档。
- 按模块级开发实现文档逐个实现 CODE 模块。
- 使用 AI-Agent 生成基础代码和测试初稿。
- 人工补充关键逻辑、权限、事务和异常处理。
- 运行构建、静态检查和单元测试。
- 进行代码评审并记录结论。

### 输出产物

- 源码、脚本和运行说明。
- 代码提交记录。
- 单元测试记录。
- 构建记录。
- 代码评审记录。
- 已知问题清单。

### 量化标准

- 每个开发任务必须关联 REQ 或 DES。
- AI 生成代码人工审查率 100%。
- 权限、成绩边界、学生课程唯一性等关键规则必须有测试或人工验证证据。
- 代码评审问题关闭后才能合并。

### 优化与变通

- AI 适合生成重复结构和初稿，不适合替代最终业务判断。
- 发现 AI 频繁生成错误代码时，应回头优化详细设计、Prompt 和编码规则。
- 对复杂逻辑应先写测试或伪代码，再让 AI 辅助实现。

## 11. 阶段 9：测试验证

目录：`demo/03_qa/workspace/01_testing/`

案例产物：

- `test-plan-and-cases-v1.0.md`
- `test-report-v1.0.md`

缺陷与正式变更登记见阶段 9b。

### 前置条件

- 可测试版本已提供。
- 需求基线和软件功能说明可引用。
- 测试环境、账号和测试数据已准备。

### 角色职责

| 角色 | 职责 |
|------|------|
| 测试人员 | 设计用例、执行测试、登记缺陷 |
| 测试负责人 | 判断质量结论和发布建议 |
| 变更管理员 | 在 `04_change` 组配合登记缺陷关联的正式变更 |
| AI-Agent | 生成用例初稿、异常场景、缺陷影响分析和报告初稿 |

### 主要动作

- 根据 REQ、DES 和接口契约生成测试用例。
- 执行功能、权限、异常和边界测试。
- 登记缺陷并关联 REQ、DES、CODE。
- 对影响设计或需求的事项在 `04_change/workspace/` 登记变更。
- 输出质量报告和发布建议。

### 输出产物

## 16. 实际工作中的优化、积累与变通

在真实项目中，不能机械照搬 Demo。建议按以下原则持续优化：

- **优化 playbook**：发现阶段输入、输出、评审规则不清楚时，优先回写对应 `playbook/README.md`。
- **积累 rules**：把必须遵守的约束沉淀为 `rules/RULE.md`，例如需求基线规则、编码规范、发布检查规则。
- **积累 skills**：把岗位执行方法沉淀为 `skills/SKILL.md`，例如需求分析、架构设计、代码生成、测试设计。
- **积累 prompts**：把高频 AI 提示词沉淀为 `prompts/PROMPT.md`，降低不同人员使用 AI 的差异。
- **允许轻量化**：小项目可以合并部分文档，但不能丢失输入、输出、责任人、评审和交接关系。
- **允许分仓或分目录**：大项目可以按六大工作组分仓管理，小项目可以放在同一仓库。
- **变更必须留痕**：需求、设计、数据库、代码、测试和发布的关键变更不能只靠口头沟通。
- **AI 输出必须验收**：AI 生成内容只能作为初稿、检查或辅助实现，正式结论必须人工确认。

## 17. 最后的提醒：框架不是万能的，纪律才是关键

`ai-project-kit` 是一个项目管理和 AI 协作的框架，它能帮助团队把需求、设计、代码、测试、交付和 AI 治理材料放到清晰的位置上，也能让阶段交接更可追踪。但它不可能解决所有问题，也不能替代项目负责人、业务负责人、架构师、开发、测试和交付人员的专业判断。

真实项目一定会遇到例外：需求不完整、业务临时变化、资源不足、遗留系统复杂、上线窗口紧张、权限和合规要求不清晰。遇到这些情况时，应具体情况具体分析，而不是机械套模板。可以裁剪文档，可以调整目录，可以分阶段补齐材料，但不能放弃基本纪律。

必须严格执行的底线：

- 重要结论要有记录。
- 正式产物要有版本。
- 阶段交接要有输入和输出。
- 需求、设计、代码、测试和交付要能追踪。
- AI 生成的重要内容要经过人工审查。
- 变更、缺陷、风险和例外要有责任人和关闭方式。

框架提供秩序，AI 提供效率，真正决定项目质量的是团队是否坚持执行纪律、是否持续复盘、是否把经验沉淀回框架。
