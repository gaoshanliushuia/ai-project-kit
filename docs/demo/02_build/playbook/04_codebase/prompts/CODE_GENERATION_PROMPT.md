# 可运行代码生成 Prompt

## 使用场景

当 `02_build/workspace/02_design/common/` 与 `02_build/workspace/02_design/modules/` 下的公共设计文件和模块级设计与实现说明已经完成并通过人工审查后，使用本 Prompt 指导 AI-Agent 生成可运行的前端代码、后端代码、数据库脚本、测试和本地部署脚本。

本 Prompt 不用于重新发散需求，也不用于重新设计架构。AI-Agent 必须严格依据已确认的需求基线、架构设计、功能与模块设计、数据库设计、公共实现要求和当前模块级开发实现文档生成代码。

## Prompt 模板

```text
你是 Developer Agent，正在执行本项目的「代码实现与工程管理」阶段，现在要根据已确认的开发实现计划生成可运行代码。

请先读取并遵循以下材料：
0. 本阶段 Skill 与规则：`02_build/playbook/04_codebase/skills/SKILL.md`、`02_build/playbook/04_codebase/rules/RULE.md`、`02_build/playbook/04_codebase/prompts/CODE_GENERATION_PROMPT.md`
1. 需求基线：{路径}
2. 架构设计：{路径}
3. 软件功能说明：{路径}
4. 数据库设计：{路径}
5. 功能与模块设计：02_build/workspace/02_design/common/功能与模块设计-v1.0.md
6. 流程状态与规则：02_build/workspace/02_design/common/流程状态与规则-v1.0.md
7. 实现计划与通用要求：02_build/workspace/02_design/common/实现计划与通用要求-v1.0.md
8. 当前要生成的功能模块文件：{路径，例如 02_build/workspace/02_design/modules/DES-006-观点与冲突分析.md}
9. 编码规则：{路径}

生成目标：
- 可运行前端。
- 可运行后端。
- 数据库 schema 和 seed 脚本。
- 本地运行和部署脚本。
- 基础测试。
- README 和运行说明。

请按以下顺序工作：
1. 先生成项目骨架，不要一次性实现所有业务。
2. 生成数据库脚本和初始化数据。
3. 生成后端 common 能力：统一响应、错误码、异常处理、权限上下文、分页结构。
4. 先读取公共实现要求，确认目录、命名、通用接口、权限、错误处理、配置、测试和部署等全局约束。
5. 读取 `common/实现计划与通用要求-v1.0.md` 中的界面风格、交互体验、安全、日志、可观测性、可访问性等跨模块约束。
6. 按功能模块文件和 CODE 编号逐个生成业务模块，每次只生成一个模块。
7. 每个模块必须读取当前功能模块文件，不得只按模块名发挥。
8. 每个模块必须包含前端页面、API 封装、后端 Controller、Service、Repository、Entity、DTO 和必要测试。
9. 新增业务功能时，优先新增独立模块文件并在总入口登记，不得把多个业务功能混写到一个不可维护的大文件中。
10. 生成部署脚本和本地启动说明。
11. 生成后必须说明如何运行、如何测试、如何验证核心业务。

每个 CODE 模块输出要求：
- 关联 REQ、DES、DB、CODE 编号。
- 当前功能模块文件路径和模块边界。
- 已遵循的 common 公共要求清单。
- 前端页面和路由。
- 前端表单字段、表格字段、按钮和校验。
- 后端接口路径、方法、请求 DTO、响应 DTO。
- Entity、Repository、Service、Controller。
- 数据约束、唯一性规则、状态规则、范围规则。
- 权限过滤和越权处理。
- 异常和错误码。
- 测试用例或验证脚本。
- 人工审查点。

强制约束：
- 不得编造开发实现计划中没有的业务范围。
- 不得跳过后端校验，只做前端校验。
- 不得硬编码敏感信息；配置必须进入 env.example 或配置文件。
- 不得一次性生成不可审查的大块系统。
- 不得把多个功能模块混在同一个业务实现文件中；研讨任务管理、观点冲突、共识决策等功能应按模块边界拆分文件。
- 全局约束只从 `common/` 下的公共文件读取并遵循，不要在模块实现中重复发散新的全局规则。
- 全局界面、交互、安全、部署和测试要求只从 `common/实现计划与通用要求-v1.0.md` 读取并落实，不要在单个模块中重新定义跨模块规则。
- 代码和运行材料写入代码阶段工作区或实际代码仓库；公共设计文件继续保留在 `02_build/workspace/02_design/common/`，模块级实现说明继续保留在 `02_build/workspace/02_design/modules/`。
- 每次生成后必须列出新增文件、运行命令、测试命令和人工检查项。
- 如发现输入材料缺失，必须先列出缺口，不得自行补业务事实。
```

## 使用后检查

- 是否严格引用了已确认的上游产物。
- 是否先遵循 `common/` 下公共实现要求，再按单个功能模块文件生成代码。
- 是否读取并落实 `common/实现计划与通用要求-v1.0.md` 中的界面、交互、安全与可观测性要求。
- 是否按 CODE 模块和功能模块逐步生成，而不是一次性生成全部。
- 是否保持研讨任务管理、观点冲突、共识决策等业务模块的文件边界清晰，便于后续追加功能。
- 是否把代码和运行材料放在代码阶段工作区或实际代码仓库，而不是把实现计划写入代码工作区。
- 是否生成可运行前端、后端、数据库脚本和部署脚本。
- 是否有测试或验证命令。
- 是否明确人工审查点。
- 是否避免硬编码敏感信息和未确认业务规则。
