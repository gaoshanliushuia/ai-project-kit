# 开发实现计划 Prompt

## 使用场景

请基于需求基线、架构设计、软件功能说明、数据库设计和编码规则，在详细设计阶段生成开发实现计划。该产物不是源码，也不是简单任务清单，而是用于指导 AI-Agent 后续生成可运行前后端代码、数据库脚本、测试和部署脚本的工程实施说明。

本 Prompt 产出的实现计划应放入 `02_build/workspace/02_design/implementation/`。`02_build/workspace/04_codebase/` 只保存代码、构建、测试、评审和运行材料，不保存实现计划文档。

## Prompt 模板

```text
你是 Developer Agent，正在执行 ai-project-kit 的「详细设计与开发实现计划」阶段。

请先遵循 02_design playbook、rules，以及 04_codebase coding standards，基于下面输入材料生成开发实现计划文档。

输入材料：
{在这里粘贴或引用以下材料：
- 需求基线，例如 01_req/workspace/01_requirements/07_baseline/
- 需求追踪矩阵，例如 01_req/workspace/01_requirements/05_traceability/
- 原型说明或可运行原型，例如 01_req/workspace/01_requirements/03_prototypes/
- 架构设计，例如 02_build/workspace/01_architecture/
- 软件功能说明文档，例如 02_build/workspace/02_design/software-function-spec-v1.0.md
- 模块设计文档，例如 02_build/workspace/02_design/02_modules/
- 接口契约文档，例如 02_build/workspace/02_design/03_interfaces/
- 流程设计文档，例如 02_build/workspace/02_design/04_flows/
- 状态与规则设计文档，例如 02_build/workspace/02_design/05_states/
- 数据库设计，例如 02_build/workspace/03_database/
- 编码规则，例如 02_build/playbook/04_codebase/rules/
- 项目技术栈、部署环境、测试要求或其他约束}

请按以下文件结构输出：
1. `02_build/workspace/02_design/implementation/implementation-plan-v1.0.md`：总入口，只写文档目标、输入依据、产物索引、全局约束索引、模块文件索引、生成顺序和交接说明。
2. `02_build/workspace/02_design/implementation/global-implementation-requirements-v1.0.md`：集中写明跨模块共享的工程约束、目录约束、命名约束、通用组件、统一响应、错误处理、权限模型、配置方式、日志、安全、测试和部署要求。
3. `02_build/workspace/02_design/implementation/common/{topic}.md`：每个非功能性通用要求一个独立文件，例如界面风格全局要求、交互体验与可访问性、安全与可观测性等；这些文件不得描述某个具体业务功能。
4. `02_build/workspace/02_design/implementation/modules/{CODE}-{module-name}.md`：每个功能模块一个独立文件，例如学生管理、教师管理、课程管理、成绩管理分别形成独立文件，便于后续变更或追加新功能。

总入口文件必须包含：
1. 文档目标：说明实现计划用于指导 AI-Agent 和开发人员生成哪些可运行产物。
2. 输入依据：列出需求基线、原型、架构、软件功能说明、数据库设计和编码规则的来源与使用方式。
3. 实施边界：明确本阶段必须实现、不实现、可简化项和需要人工确认的假设。
4. 推荐技术栈：说明前端、后端、数据库、本地部署和测试技术栈；如果技术栈未确认，必须标记“待确认”。
5. 目标工程结构：给出项目根目录、前端目录、后端目录、数据库脚本目录和部署脚本目录。
6. 通用要求文件索引：列出 `common/` 下每个非功能性通用要求文件路径、主题、适用范围和人工审查点。
7. 模块文件索引：列出每个模块文件路径、模块名称、对应 CODE/REQ/DES/DB 编号和依赖关系。
8. AI-Agent 生成顺序：把代码生成拆成可审查的增量步骤，不允许一次性生成不可控的大块系统。
9. AI-Agent 提示词模板：至少提供“生成项目骨架”“生成一个业务模块”“生成部署脚本”的 Prompt 示例。
10. 人工审查清单：列出开发人员必须审查的权限、安全、数据约束、可运行性、测试和部署项。
11. 本阶段输出：列出代码、脚本、测试、构建、评审、缺陷和运行说明应放入哪些目录。
12. 交接给代码阶段和测试阶段：列出可测试版本、启动方式、初始化方式、测试账号、已知问题和 REQ/DES/CODE 映射。

全局实现要求文件必须包含：
- 统一数据定义：基于数据库设计和功能说明整理实体、字段、类型、必填、唯一性、枚举、状态、数据范围和业务约束。
- 通用接口规范：定义统一响应结构、分页结构、错误码、权限上下文和鉴权处理方式。
- 前端实现要求：列出页面路由、组件结构、API 封装、表单校验、角色菜单和错误展示要求。
- 后端实现要求：列出 Controller、Service、Repository、Entity、DTO、异常处理、事务边界和权限过滤要求。
- 数据库脚本要求：列出 schema、seed、初始化数据、索引、约束和回滚或重建说明。
- 部署与运行脚本要求：列出 docker-compose、env.example、start/stop 脚本、本地运行命令和访问地址要求。
- 测试与验证要求：列出单元测试、接口测试、前端验证和运行验收命令。

每个 common 文件必须包含：
- 通用要求主题和适用范围。
- 约束目标：说明该要求约束界面、交互、安全、日志、性能、可访问性、兼容性或其他非功能性方面。
- 具体规则：写到 AI-Agent 可以直接落实到代码、样式、组件、配置、测试或运行说明的粒度。
- 禁止事项：列出不得出现的实现方式。
- 验证方式：列出人工检查点、自动化检查或运行验证方式。
- 与功能模块的关系：说明所有模块如何引用该通用要求，不得把这些通用规则复制到每个模块文件中。

每个模块文件必须包含：
- 模块名称、CODE 编号、关联 REQ、DES、DB 编号。
- 功能目标和实施边界。
- 前端页面、路由、表单字段、表格字段、按钮和校验。
- 后端接口路径、方法、请求 DTO、响应 DTO。
- Entity、Repository、Service、Controller 和必要 DTO。
- 数据约束、唯一性规则、状态规则、范围规则。
- 权限过滤和越权处理。
- 异常和错误码。
- 测试用例或验证脚本。
- AI-Agent 生成要求。
- 人工审查点和验收标准。

输出要求：
- 不要编造未提供的事实。
- 对假设内容使用“假设”标记。
- 对需要人工确认的内容使用“待确认”标记。
- implementation-plan 是详细设计文档集的下游产物，必须基于 `software-function-spec`、模块设计、接口契约、流程设计、状态与规则设计生成，不得替代或跳过设计文档。
- AI-Agent 不得直接依据访谈纪要或口头需求生成代码，必须引用已确认的需求、设计、数据库和编码规则。
- 数据定义必须包含字段类型、必填、唯一性、枚举值、状态值、范围约束和跨表业务规则。
- 开发任务必须能追踪到 REQ、DES、DB 和 CODE 编号。
- 全局约束只能集中写在总入口或全局实现要求文件中，不要分散复制到各功能模块文件。
- 非功能性通用要求必须放入 `common/` 目录，按主题拆分独立文件，例如界面风格、交互体验、安全与可观测性；不得混入具体业务模块文件。
- 业务功能必须按功能模块拆分为独立文件；后续新增功能时，优先新增独立功能模块文件，并在总入口中补充索引和依赖关系。
- 前端、后端、数据库和部署脚本要求必须能支撑生成可运行系统。
- 权限、数据安全、成绩范围、重复数据、事务边界、初始化数据和部署配置必须明确写出人工审查点。
- 如涉及 AI 使用、安全、敏感数据或重要输出验收，提醒写入 `05_gov/workspace/`。
```

## 使用后检查

- 是否把实现计划放在 `02_build/workspace/02_design/implementation/`。
- 是否把全局实现要求集中写在总入口或全局要求文件中。
- 是否在 `common/` 下按主题拆分非功能性通用要求，例如界面风格、交互体验、安全与可观测性。
- 是否按功能模块拆分独立文件，例如学生管理、教师管理等模块可以单独变更和追加。
- 是否每个 CODE 模块都有独立详细文件，足够指导 AI-Agent 生成代码。
- 是否引用了上游输入或编号。
- 是否区分已确认、假设和待确认内容。
- 是否形成可评审、可交接、可追踪的结果。
- 是否把代码生成拆成可审查的增量步骤，而不是一次性生成不可控的大块代码。
