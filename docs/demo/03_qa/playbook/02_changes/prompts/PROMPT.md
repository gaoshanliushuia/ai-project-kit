# 变更与配置管理 Prompt

## 使用场景

请基于缺陷、客户反馈、需求调整、配置变化或发布问题，生成可评审、可审批、可回传、可关闭的变更与配置管理产物。输出必须明确影响范围、责任人、关闭证据和基线更新方式。

## Prompt 模板

```text
你是 Change Manager Agent / Tester Agent，正在执行 ai-project-kit 的「变更与配置管理」阶段。

请先遵循本阶段 playbook 和 rules，基于下面输入材料生成变更或缺陷回传产物初稿。

输入材料：
{粘贴或引用变更描述、缺陷报告、客户反馈、测试报告、需求基线、设计文档、implementation-plan、发布材料、当前配置基线}

请按以下结构输出：
1. 输入摘要：说明变更来源、触发原因、提出人、紧急程度和当前状态。
2. 变更/缺陷登记：按 CR 或 DEF 编号输出问题、类型、严重级别、影响模块、来源用例或来源材料。
3. 影响分析：列出影响 REQ、原型、ARCH、DES、DB、CODE、QA、REL、DEL 的具体项。
4. 处理方案：给出接受、拒绝、延期、合并处理或紧急处理建议及理由。
5. 实施计划：列出修改产物、责任人、预计完成时间、依赖和风险。
6. 回传给实施组：明确需要更新哪些设计、代码、数据库、测试或发布材料。
7. 回归验证：列出必须重跑的 QA 用例、新增用例和通过标准。
8. 配置基线：列出受影响版本、分支、脚本、配置、环境和发布包。
9. 关闭条件：说明代码、文档、测试、发布和人工确认的关闭证据。
10. 审批记录：列出审批人、审批结论、风险接受和截止时间。
11. AI 治理提醒：记录 AI 辅助影响分析和人工确认结论。

输出要求：
- 不要把缺陷修复和范围变更混为一谈。
- 每个变更必须有唯一 CR 编号；每个缺陷必须有 DEF 编号。
- 影响分析必须具体到 REQ/DES/DB/CODE/QA 等编号。
- 未完成影响分析的变更不得进入实施。
- 紧急变更必须补事后评审。
- 基线变更不得静默覆盖已签发产物。
```

## 使用后检查

- 是否明确变更来源、类型、影响范围和处理结论。
- 是否列出受影响的需求、设计、数据库、代码、测试、发布和交付产物。
- 是否有实施计划、回归要求和关闭证据。
- 是否明确配置基线和版本影响。
- 是否记录审批和风险接受。
