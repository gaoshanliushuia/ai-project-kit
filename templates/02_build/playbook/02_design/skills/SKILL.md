# 详细设计 Skill

## 目标

把架构方案细化为开发可执行、测试可验证、变更可分析的设计产物，并在同一阶段完成数据库模型、字段字典、索引脚本、ER 实体关系图和数据质量规则设计。

## 适用角色

- `Architect Agent / Developer Agent`

## 输入

需求编号、验收条件、架构决策、模块边界、接口约束、页面原型、UI 风格要求、业务对象、数据需求、状态规则、查询需求、数据权限和审计要求。

## 输出

模块设计、接口契约、UI 总体风格、模块级界面布局说明、流程图、状态机、异常处理、数据库设计、ER 实体关系图、字段字典、数据库脚本、数据质量规则、设计追踪矩阵。

## 标准执行顺序

1. 激活本阶段 `skills/SKILL.md` 作为执行入口，确认目标、输入输出和执行边界。
2. 再读取本阶段 `rules/RULE.md`，检查进入条件、目录结构、编号规则和退出要求。
3. 再读取本阶段 `agents/agent.md`，用于生成统一的详细设计文档集，数据库设计不再作为独立阶段执行。
4. 该详细设计文档集必须同时承载业务设计说明、UI 设计、数据库设计与实现指导内容，不再额外拆分独立的实现计划 Agent 或数据库设计 Agent。
5. 若输入材料不完整，先列出缺口、假设、待确认事项和影响范围，不得直接编造业务规则或接口契约。
6. 生成或检查阶段产物时，必须引用需求编号、架构决策、模块编号、版本和评审记录。
7. 输出前必须按 `rules/RULE.md` 与 `agents/agent.md` 的“使用后检查”完成自检。
8. 若发现本阶段 playbook 存在冲突、过时或缺漏，先在结果中指出，再回写修正 `rules/`、`skills/` 或 `agents/`。

## 执行步骤

- 明确模块职责、输入输出、依赖关系和边界条件。
- 设计接口字段、类型、校验、鉴权、错误码、超时、重试和幂等。
- 补齐主流程、异常流程、补偿流程和并发场景。
- 定义状态流转、禁止条件和终态。
- 明确总体 UI 风格、布局规则、组件位置、交互反馈和可访问性要求。
- 识别核心实体、关系、生命周期和数据所有者。
- 定义表、字段、类型、约束、索引、字典、审计字段、初始化数据和迁移/回滚策略。
- 输出 ER 实体关系图，用箭头连接各表的主要外键及关联关系；数据库脚本不得创建物理外键。
- 提取开发任务、数据库落地要求和测试关注点。

## 使用要求

- 本阶段执行入口默认是：激活 `skills/SKILL.md`，再遵循 `rules/RULE.md` 与 `agents/agent.md`。
- 生成阶段产物前，必须先确认输入完整性、编号前缀、引用版本、人工确认点和下游交接对象。
- 所有结论必须能追踪到输入材料、编号、负责人或评审记录。
- AI 生成内容只作为初稿或检查建议，关键结论必须由阶段负责人确认。
- 统一设计文档集必须同时覆盖业务功能、接口契约、UI 风格与布局、流程状态、数据库模型、数据约束、脚本、实现指导、测试关注点和 AI 代码生成约束。
- 数据库设计产物统一输出到 `02_build/workspace/02_design/database/`，不再输出到独立 `02_build/workspace/03_database/`。
- 数据库脚本可以包含主键、唯一约束、非空约束、检查约束和索引，但不得创建物理外键；表间关系必须通过 ER 图、字段命名、业务规则和 Service 层校验说明表达。
- 输出前必须完成一次 playbook 自检，至少覆盖进入条件、编号追踪、产物结构、AI 治理留痕和交接要求。
- 发现可复用经验时，回写本阶段 `rules/`、`skills/` 或 `agents/`，并在后续版本发布中说明。
