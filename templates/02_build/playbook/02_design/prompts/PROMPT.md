# 详细设计 Prompt

## 使用场景

请基于需求基线、可运行原型、页面说明、架构设计、数据库设计约束和编码规则，生成详细设计阶段唯一的一套设计文档集。该文档集既要体现业务功能、接口、流程、状态和规则，也要直接指导后续编码、数据库落地、测试设计和 AI-Agent 分步生成代码，不能只写模块概述。

本 Prompt 只用于生成 `02_build/workspace/02_design/` 下的统一详细设计文档集，不再拆分为单独的“设计 Prompt”和“实现计划 Prompt”。公共文件放入 `common/`，模块文件放入 `modules/`，接口契约放入 `interfaces/`。其中 `common/实现计划与通用要求-v1.0.md` 与各模块文件应同时承载实现指导内容。

## Prompt 模板

```text
你是 Architect Agent / Developer Agent，正在执行本项目的「详细设计」阶段。

请先读取并遵循本阶段 `skills/SKILL.md`、`rules/RULE.md` 与 `prompts/PROMPT.md`，基于下面输入材料生成详细设计文档集初稿。

输入材料：
{粘贴或引用以下材料：
- 需求基线与需求追踪矩阵
- 页面原型说明或可运行原型
- 架构设计、权限模型、业务规则、待确认问题
- 数据库设计约束或既有数据模型
- 编码规则、技术栈、部署环境、测试要求或其他工程约束}

请按以下文件结构输出：
1. `02_build/workspace/02_design/common/功能与模块设计-v1.0.md`：合并后的功能与模块总览文档，说明功能清单、模块边界、模块依赖、通用设计规则和模块文件索引。
2. `02_build/workspace/02_design/common/流程状态与规则-v1.0.md`：合并后的流程、状态与规则文档，说明主流程、异常流程、人工确认点、状态字段、流转、唯一性和跨模块规则。
3. `02_build/workspace/02_design/common/实现计划与通用要求-v1.0.md`：合并后的实现计划与通用要求文档，说明工程结构、统一数据定义、统一响应、错误处理、权限模型、界面交互、安全可观测性、测试要求、部署要求、代码生成顺序和人工审查点。
4. `02_build/workspace/02_design/modules/DES-xxx-中文模块名.md`：按功能模块拆分的模块设计文件，例如 `DES-002-研讨任务管理.md`、`DES-008-智能体管理与研讨增强.md`。每个模块文件必须同时包含业务设计说明和实现指导，说明模块职责、功能点说明、数据对象、接口映射、规则异常、前后端落地要求、测试点和 AI 代码生成要求。
5. `02_build/workspace/02_design/interfaces/interface-contracts-v1.0.md`：接口契约文档，集中定义接口路径、方法、请求 DTO、响应 DTO、权限、错误码和分页规则。

每个设计文档必须包含：
- 文档目标：说明该设计文档如何服务数据库设计、编码实现、测试设计和 AI-Agent 代码生成。
- 输入依据：列出需求、原型、架构、数据库约束、编码规则和版本来源。
- 设计内容：写到开发人员、测试人员和 AI-Agent 可执行的粒度。
- 追踪关系：建立 REQ、ARCH、DES、DB、CODE、QA 的映射或引用。
- 设计评审清单：列出必须人工确认的接口、权限、业务规则和异常口径。
- 下游交接：明确哪些内容交给数据库设计、代码阶段、测试阶段和发布阶段。

`common/实现计划与通用要求-v1.0.md` 必须包含：
- 文档目标：说明该公共文件如何统一约束所有模块实现。
- 实施边界：明确本阶段必须实现、不实现、可简化项和需要人工确认的假设。
- 推荐技术栈：说明前端、后端、数据库、本地部署和测试技术栈；若未确认则标记“待确认”。
- 目标工程结构：给出项目根目录、前端目录、后端目录、数据库脚本目录和部署脚本目录。
- 统一数据定义：整理实体、字段、类型、必填、唯一性、枚举、状态、数据范围和业务约束。
- 通用接口规范：定义统一响应结构、分页结构、错误码、权限上下文和鉴权处理方式。
- 前端实现要求：列出页面路由、组件结构、API 封装、表单校验、角色菜单和错误展示要求。
- 后端实现要求：列出 Controller、Service、Repository、Entity、DTO、异常处理、事务边界和权限过滤要求。
- 数据库脚本要求：列出 schema、seed、初始化数据、索引、约束和回滚或重建说明。
- 部署与运行脚本要求：列出 docker-compose、env.example、start/stop 脚本、本地运行命令和访问地址要求。
- 测试与验证要求：列出单元测试、接口测试、前端验证和运行验收命令。
- AI-Agent 生成顺序：把代码生成拆成可审查的增量步骤，不允许一次性生成不可控的大块系统。
- 人工审查清单：列出开发人员必须审查的权限、安全、数据约束、可运行性、测试和部署项。

每个 `DES-编号-中文模块名.md` 模块文件必须包含：
- 模块名称、关联 REQ、DES、DB、CODE 编号和依赖关系。
- 功能目标、实施边界和下游影响范围。
- 每个 `DES-xxx-FPxx` 功能点的用户入口、输入、输出、页面字段、表单规则、表格字段、按钮和交互说明。
- 后端接口路径、方法、请求 DTO、响应 DTO、权限、错误码和幂等/超时要求。
- Entity、Repository、Service、Controller 和必要 DTO 的设计说明。
- 数据约束、唯一性规则、状态规则、范围规则和跨表业务规则。
- 权限过滤、越权处理、异常分支和补偿策略。
- 测试用例或验证脚本建议。
- AI-Agent 生成要求、生成顺序和人工审查点。

输出要求：
- 不要编造未确认的业务规则。
- 对假设内容使用“假设”标记，对待确认内容使用“待确认”标记。
- 每个高优先级 REQ 必须有 DES 设计项。
- 每个功能章节必须具体到字段、接口、权限、异常、测试和 AI 代码生成要求。
- 模块设计必须按功能模块拆分独立文件，文件名使用 `DES-编号-中文模块名.md`，不要使用英文模块名作为文件名。
- `common/功能与模块设计-v1.0.md` 只能作为公共总览索引，不得承载所有模块的详细功能点。
- 每个模块文件必须继续拆到 `DES-xxx-FPxx` 功能点粒度，每个功能点必须能直接指导 AI-Agent 生成 Controller、Service、Repository、DTO、Entity、前端页面和测试。
- 接口契约必须包含路径、方法、参数、返回、错误码和权限要求。
- 数据约束必须写清唯一性、必填、枚举、状态、范围和跨表规则。
- 文档必须直接承载实现指导内容，不再额外拆分独立 implementation-plan Prompt。
- AI-Agent 不得直接依据访谈纪要或口头需求生成代码，必须引用已确认的需求、设计、数据库和编码规则。
- 全局实现约束只能集中写在 `common/` 下的公共文件中，不要分散复制到各功能模块文件。
- 非功能性通用要求必须并入 `common/实现计划与通用要求-v1.0.md`，不得在具体业务模块文件中重复展开全局规则。
- 每个 CODE 模块必须能追踪到对应的 `DES-xxx-FPxx` 功能点，并引用具体模块设计文件，而不是只引用公共总览文件。
- 文档必须能直接作为数据库设计、编码实现、测试用例设计和代码生成的输入。
```

## 使用后检查

- 是否每个功能都有独立 DES 章节。
- 是否在 `modules/` 下按功能模块拆分为中文文件名的独立设计文件。
- 是否每个模块文件细化到 `DES-xxx-FPxx` 功能点，并能直接指导 AI-Agent 生成代码。
- 是否包含页面字段、接口契约、权限规则和异常场景。
- 是否提供请求/响应样例、测试关注点和实现指导。
- 是否能指导 AI-Agent 生成前后端代码而不偏离需求。
- 是否已把实现计划、通用要求和代码生成约束合并进当前设计文档集。
- 是否明确数据库、编码、测试和发布的下游输入。
