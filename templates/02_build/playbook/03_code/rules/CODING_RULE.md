# 代码编写规范 rules

本规则用于约束项目代码编写过程中的通用风格、命名方式、注释要求、文件组织和分包方式。适用于 `Java`、`Vue`、`JavaScript`、`HTML` 等常见工程代码，具体项目可在本规则基础上补充框架、脚手架或团队专属约定。

## 适用范围

- 适用阶段：`代码实现与工程管理`
- 适用对象：业务代码、前端页面、公共组件、工具函数、配置代码和测试代码。
- 适用语言：`Java`、`Vue`、`JavaScript`、`HTML`。
- 若项目已有更严格的语言规范、框架规范或静态检查规则，应优先执行更严格规则，并在评审中说明依据。

## 通用命名规则

- 命名必须表达业务含义，避免使用无意义缩写、拼音缩写、临时编号或泛化名称，例如 `data1`、`tmp`、`aaa`。
- 类、组件、模块、变量、方法、文件名应保持语义一致，避免同一概念在不同位置使用多个名称。
- 布尔变量应使用 `is`、`has`、`can`、`should` 等前缀，明确表示判断语义。
- 集合变量应使用复数或集合语义，例如 `users`、`orderList`、`selectedIds`。
- 常量应使用全大写加下划线，例如 `MAX_RETRY_COUNT`、`DEFAULT_PAGE_SIZE`。

## 大小写规则

- Java 类名、接口名、枚举名使用 `PascalCase`，方法名、变量名、参数名使用 `camelCase`。
- Vue 组件文件名和组件名使用 `PascalCase`，普通目录名使用小写短横线或小写单词，并在项目内保持一致。
- JavaScript 变量、函数、方法使用 `camelCase`，类名和构造函数使用 `PascalCase`。
- HTML 标签、属性名、自定义属性和 `data-*` 属性使用小写字母，多个单词使用短横线连接。
- 文件、目录、变量、方法不得仅依赖大小写区分含义，避免在不同操作系统中产生冲突。

## 注释规则

- 注释用于解释业务意图、边界条件、特殊约束、兼容原因或复杂算法，不应重复描述代码表面行为。
- 公共类、公共方法、公共组件、复杂工具函数应补充必要说明，包括用途、关键参数、返回含义和异常条件。
- 临时方案必须使用统一标记，例如 `TODO`、`FIXME`，并注明原因、责任人或关联任务编号。
- 禁止保留无效注释、过期注释、大段被注释代码和调试日志。
- 注释语言应与项目文档保持一致；同一文件内不应混用多种注释风格。

## 文件名规则

- 文件名必须与主类、主组件、主模块或页面职责一致。
- 一个文件只承载一个主要职责，避免把多个不相关类、组件或工具函数堆叠在同一文件中。
- Java 文件名必须与 `public` 类名一致。
- Vue 单文件组件使用 `.vue` 后缀，组件文件名使用 `PascalCase`，例如 `UserProfile.vue`。
- JavaScript 工具文件可使用 `camelCase` 或 `kebab-case`，但同一项目必须统一。
- HTML 页面文件使用小写短横线命名，例如 `user-profile.html`、`order-detail.html`。

## 包与目录组织规则

- 包名和目录名应按业务域、技术层次或模块边界组织，不能按个人、时间或临时任务命名。
- Java 包名使用全小写，建议按 `com.company.project.module.layer` 组织。
- 后端常见分层可包括 `controller`、`service`、`repository`、`domain`、`dto`、`vo`、`config`、`common`。
- 前端目录应区分 `views`、`components`、`api`、`store`、`router`、`utils`、`assets` 等职责。
- 公共代码进入公共目录前必须确认复用场景，避免把业务专属逻辑放入 `common`、`shared`、`utils`。
- 跨模块调用应通过明确接口或服务边界完成，不得绕过分层直接访问内部实现。

## Java 编写规则

- 类名使用名词或名词短语，方法名使用动词或动宾短语。
- `Controller` 只负责请求接入、参数校验和响应转换，不承载复杂业务规则。
- `Service` 负责业务编排和事务边界，复杂领域逻辑应沉淀到领域对象或独立业务服务。
- `Repository`、`Mapper` 或 `DAO` 只负责数据访问，不应包含业务判断。
- 异常处理应区分业务异常、参数异常和系统异常，不得吞掉异常或只打印日志。
- 枚举应表达稳定业务值，必须包含清晰字段和说明，避免使用魔法数字或魔法字符串。
- 测试类命名应与被测类对应，测试方法名应表达场景、行为和预期结果。

## Vue 编写规则

- 组件应保持单一职责，页面组件负责页面组织，基础组件负责展示和交互封装。
- `props`、`emits`、`computed`、`watch`、`methods` 或组合式函数应按项目约定排序。
- `props` 必须声明类型、必要性和默认值；复杂对象默认值必须使用函数返回。
- 事件名使用小写短横线，例如 `update:model-value`、`submit-form`。
- 可复用逻辑应提取为组合式函数、工具函数或子组件，不应复制粘贴到多个页面。
- 样式作用域应明确，避免组件样式污染全局；全局样式必须有统一入口和命名约束。

## JavaScript 编写规则

- 默认使用 `const`，需要重新赋值时使用 `let`，禁止使用 `var`。
- 函数应保持职责清晰，避免过长参数列表；超过三个参数时优先使用对象参数。
- 异步代码必须显式处理成功、失败和取消场景，不得静默忽略 `Promise` 错误。
- 工具函数应保持纯函数优先，避免隐式读写全局状态。
- 对外导出的函数、类、常量必须命名明确，避免默认导出匿名函数或匿名对象。
- 禁止在生产代码中保留 `console.log`、`debugger` 和临时 mock 数据。

## HTML 编写规则

- HTML 结构应语义化，优先使用 `header`、`main`、`section`、`article`、`nav`、`footer` 等语义标签。
- 标签必须正确闭合和嵌套，属性值使用双引号。
- `id` 在页面内必须唯一；样式选择优先使用类名，避免过度依赖 `id`。
- 类名使用小写短横线，例如 `user-card`、`form-item`。
- 表单元素必须提供明确的 `label` 或可访问性说明。
- 图片必须提供有意义的 `alt`，装饰性图片可使用空 `alt`。

## 评审检查规则

- 提交前应完成格式化、静态检查和关键路径测试。
- 代码评审必须检查命名、大小写、注释、文件职责、分包边界和语言专项规则。
- 对规则的例外处理必须说明原因、影响范围和后续处理方式。
- 发现可复用的新规范时，应回写本目录，并在后续版本发布中说明变化。
