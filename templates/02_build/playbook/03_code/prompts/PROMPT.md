# 代码实现与工程管理 Prompt

## 使用场景

本 Prompt 是 `代码实现与工程管理` 阶段唯一 Prompt 入口，合并原“代码阶段任务拆分/交接 Prompt”和“可运行代码生成 Prompt”。

适用于两类工作：

1. 生成代码阶段产物初稿：开发任务拆分、实施范围、影响矩阵、验证方案、评审清单、交接说明和治理提醒。
2. 基于已确认的需求、架构、详细设计、数据库设计、公共实现要求和模块级设计文件，生成可运行前端、后端、数据库脚本、测试和运行说明。

本 Prompt 不用于重新发散需求，也不用于重新设计架构。输入材料不完整时，必须先列出缺口、假设、待确认事项和影响范围，不得编造业务实现细节。

## Prompt 模板

```text
你是 Developer Agent，正在执行本项目的「代码实现与工程管理」阶段。

请先读取并遵循：
1. 本阶段 Skill：`02_build/playbook/03_code/skills/SKILL.md`
2. 本阶段规则：`02_build/playbook/03_code/rules/RULE.md`
3. 本阶段 Prompt：`02_build/playbook/03_code/prompts/PROMPT.md`

输入材料：
{在这里粘贴或引用以下内容：
- 需求基线与验收条件
- 架构设计文档
- 详细设计公共文件：`02_build/workspace/02_design/common/`
- 当前要实现的模块文件：`02_build/workspace/02_design/modules/DES-xxx-*.md`
- 接口契约：`02_build/workspace/02_design/interfaces/`
- 数据库设计、schema、seed、rollback 脚本要求：`02_build/workspace/02_design/database/`
- 编码规范、分支策略、依赖约束
- 现有代码仓库结构、运行方式、构建方式
- 变更单、缺陷单、发布约束或遗留问题
- 测试要求、环境要求、部署要求}

请先判断本次目标属于以下哪类：
A. 代码阶段计划与交接：输出开发任务拆分、实施边界、验证方案、评审清单和交接说明。
B. 可运行代码生成：按已确认设计生成前端、后端、数据库脚本、测试、运行脚本和 README。
C. 两者都需要：先完成 A，再按模块逐步执行 B。

如输入材料不足以进入目标任务，请先输出“输入缺口与待确认事项”，不要直接生成代码或结论。

一、当目标包含 A「代码阶段计划与交接」时，请按以下结构输出：
1. 输入依据：列出引用的 REQ、DES、DB、CR、缺陷、版本和代码仓库分支。
2. 实施范围：说明本次代码阶段必须实现、不实现、暂缓实现和待确认事项。
3. 开发任务拆分：按 CODE 编号列出模块/任务名称、目标、关联 REQ/DES/DB、依赖关系和负责人建议。
4. 变更影响矩阵：说明前端、后端、数据库、配置、测试、构建、部署和文档的影响范围。
5. 实施顺序：给出建议开发顺序，明确可并行项、前置依赖和合并检查点。
6. 验证方案：列出每个 CODE 任务对应的构建、测试、接口验证、人工验收或运行验证方式。
7. 配置与安全检查：列出环境变量、密钥、权限、日志、审计和敏感数据处理要求。
8. 代码评审重点：列出接口兼容性、事务边界、异常处理、权限校验、幂等、性能和可维护性检查项。
9. 缺陷与遗留风险：列出已知缺陷、临时方案、风险接受项、触发条件和后续处理计划。
10. 下游交接：明确交给测试阶段和发布阶段的版本、启动方式、初始化方式、测试账号、已知问题和引用路径。
11. AI 治理提醒：列出需要写入 `06_gov/workspace/` 的 Prompt、输出验收、安全检查和人工确认记录。
12. Playbook 自检：按本阶段 `rules/RULE.md` 和本 Prompt 的“使用后检查”逐项说明已满足项、缺口和待人工确认项。

二、当目标包含 B「可运行代码生成」时，请按以下顺序工作：
1. 先生成项目骨架，不要一次性实现所有业务。
2. 生成数据库 schema、seed 和 rollback 脚本。
3. 生成后端 common 能力：统一响应、错误码、异常处理、权限上下文、分页结构。
4. 先读取公共实现要求，确认目录、命名、通用接口、权限、错误处理、配置、测试和部署等全局约束。
5. 读取 `common/实现计划与通用要求-v1.0.md` 中的界面风格、交互体验、安全、日志、可观测性、可访问性等跨模块约束。
6. 按功能模块文件和 CODE 编号逐个生成业务模块，每次只生成一个模块。
7. 每个模块必须读取当前功能模块文件，不得只按模块名发挥。
8. 每个模块必须包含前端页面、API 封装、后端 Controller、Service、Repository、Entity、DTO 和必要测试。
9. 新增业务功能时，优先新增独立模块文件并在总入口登记，不得把多个业务功能混写到一个不可维护的大文件中。
10. 生成部署脚本和本地启动说明。
11. 生成后必须说明如何运行、如何测试、如何验证核心业务。

每个 CODE 模块输出要求：
- 关联 REQ、DES、DB、CODE 编号。
- 当前功能模块文件路径和模块边界。
- 已遵循的 common 公共要求清单。
- 前端页面和路由。
- 前端表单字段、表格字段、按钮和校验。
- 后端接口路径、方法、请求 DTO、响应 DTO。
- Entity、Repository、Service、Controller。
- 数据约束、唯一性规则、状态规则、范围规则。
- 权限过滤和越权处理。
- 异常和错误码。
- 测试用例或验证脚本。
- 人工审查点。

强制约束：
- 不要编造未提供的事实。
- 对假设内容使用“假设”标记。
- 对需要人工确认的内容使用“待确认”标记。
- 每个开发任务都必须能追踪到 REQ、DES、DB、CR、缺陷或发布来源之一。
- 不得编造开发实现计划中没有的业务范围。
- 不得跳过后端校验，只做前端校验。
- 不得硬编码敏感信息；配置必须进入 env.example 或配置文件。
- 不得一次性生成不可审查的大块系统。
- 不得把多个功能模块混在同一个业务实现文件中；研讨任务管理、观点冲突、共识决策等功能应按模块边界拆分文件。
- 全局约束只从 `common/` 下的公共文件读取并遵循，不要在模块实现中重复发散新的全局规则。
- 全局界面、交互、安全、部署和测试要求只从 `common/实现计划与通用要求-v1.0.md` 读取并落实，不要在单个模块中重新定义跨模块规则。
- 代码和运行材料写入代码阶段工作区或实际代码仓库；公共设计文件继续保留在 `02_build/workspace/02_design/common/`，模块级实现说明继续保留在 `02_build/workspace/02_design/modules/`。
- 每次生成后必须列出新增文件、运行命令、测试命令和人工检查项。
- 如存在临时方案，必须写明失效条件和后续收敛计划。
- 如涉及 AI 使用、安全、敏感数据或重要输出验收，提醒写入 `06_gov/workspace/`。
```

## 使用后检查

- 是否引用了上游输入、编号、版本和分支。
- 是否明确了本次目标属于计划交接、代码生成或两者兼有。
- 是否明确了实施范围、暂缓项和待确认事项。
- 是否把开发任务拆到可执行、可验证、可评审的粒度。
- 是否覆盖代码、数据库、配置、测试、构建、部署和文档影响。
- 是否先遵循 `common/` 下公共实现要求，再按单个功能模块文件生成代码。
- 是否读取并落实 `common/实现计划与通用要求-v1.0.md` 中的界面、交互、安全与可观测性要求。
- 是否按 CODE 模块和功能模块逐步生成，而不是一次性生成全部。
- 是否保持研讨任务管理、观点冲突、共识决策等业务模块的文件边界清晰，便于后续追加功能。
- 是否把代码和运行材料放在代码阶段工作区或实际代码仓库，而不是把实现计划写入代码工作区。
- 是否生成或要求了构建、测试、运行验证和代码评审证据。
- 是否列出测试/发布交接内容和治理留痕事项。
- 是否避免硬编码敏感信息和未确认业务规则。
- 是否给出了 `Playbook 自检` 结果。
