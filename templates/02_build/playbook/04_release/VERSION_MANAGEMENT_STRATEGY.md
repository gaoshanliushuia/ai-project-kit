# 版本管理与迭代策略

## 1. 目标

本策略用于客户定制化软件项目的版本、分支、Issue、PR、迭代和发布管理，确保每个交付项做到：

- 来源清楚：能追踪到客户需求、变更或缺陷。
- 过程可控：有 Issue、分支、PR、测试和发布记录。
- 发布可靠：有版本范围、发布清单、验证记录和回滚方案。
- 变更可审计：已基线化内容的修改必须走变更管理。

## 2. 管理主线

项目采用以下主线管理：

```text
客户需求/变更/缺陷
→ Gitee Issue
→ 迭代 Sprint
→ 开发分支
→ Pull Request
→ 测试验证
→ Release 版本
→ 复盘与下轮迭代
```

每个交付项必须建立追踪链路：

```text
客户来源 → 需求/变更/缺陷编号 → Gitee Issue → 分支 → PR → 测试记录 → 发布版本
```

## 3. 编号规则

项目阶段产物建议使用以下编号前缀：

- `REQ-xxx`：客户需求、范围边界、验收标准。
- `DES-xxx`：详细设计、接口设计、流程设计。
- `DB-xxx`：数据库设计、表结构、迁移脚本。
- `CODE-xxx`：开发任务、实现记录、构建记录。
- `QA-xxx`：测试用例、缺陷、回归记录。
- `CR-xxx`：客户变更、影响分析、审批记录。
- `REL-xxx`：版本计划、发布清单、回滚方案、发布复盘。

Gitee Issue 标题建议包含编号，例如：

```text
REQ-001 客户登录功能
QA-003 导出报表失败
CR-002 客户要求调整审批流程
```

## 4. 版本号规则

版本号采用语义化版本格式：

```text
v主版本.功能版本.修复版本
```

示例：

- `v1.0.0`：首个正式交付版本。
- `v1.1.0`：新增客户确认的功能。
- `v1.1.1`：只修复缺陷，不新增功能。
- `v1.2.0-beta.1`：测试或预发布版本。
- `v1.2.0-rc.1`：候选发布版本。

版本升级规则：

- 主版本：核心架构、业务边界或兼容性发生重大变化。
- 功能版本：新增客户确认的功能或模块。
- 修复版本：缺陷修复、兼容性修复、小范围调整。
- 预发布版本：用于测试、验收或发布前验证。

## 5. 分支策略

项目采用轻量 Git Flow：

```text
main                 生产稳定分支
develop              当前集成开发分支
release/v1.2.0       发布准备分支
feature/REQ-001-xxx  需求开发分支
fix/QA-003-xxx       普通缺陷修复分支
hotfix/v1.2.1-xxx    生产紧急修复分支
```

分支命名规则：

```text
<类型>/<编号>-<简短英文描述>
```

示例：

```text
feature/REQ-001-customer-login
fix/QA-003-export-error
hotfix/QA-009-payment-timeout
release/v1.2.0
```

分支使用规则：

- `main` 只保存已发布、可回滚的稳定版本。
- `develop` 用于日常集成和联调。
- `feature/*` 从 `develop` 创建，完成后通过 PR 合并回 `develop`。
- `fix/*` 从 `develop` 或 `release/*` 创建，修复后通过 PR 合并。
- `release/*` 从 `develop` 创建，只允许修复发布阻塞问题。
- `hotfix/*` 从 `main` 创建，修复后同时合并回 `main` 和 `develop`。

## 6. Issue 管理规则

Gitee Issue 是项目协作和状态流转的主记录。本地 Markdown 文件可作为详细需求、设计、测试或发布文档，但不得替代 Gitee Issue 的协作状态。

每个 Issue 至少包含：

- 标题：包含编号和简短说明。
- 类型：需求、缺陷、变更、任务。
- 来源：客户、测试、产品、运维或内部评审。
- 验收标准：完成后如何判断通过。
- 优先级：高、中、低。
- 负责人：明确处理人。
- 迭代：归属 Sprint 或版本。
- 关联项：分支、PR、测试记录、发布版本。

Issue 状态建议：

```text
待确认 → 已排期 → 开发中 → 待测试 → 测试通过 → 已发布 → 已关闭
```

缺陷类 Issue 可增加：

```text
已复现 → 修复中 → 待回归 → 回归通过 → 已关闭
```

## 7. PR 管理规则

所有进入 `develop`、`release/*`、`main` 的代码必须通过 Pull Request。

PR 必须包含：

- 关联 Issue 编号。
- 改动摘要。
- 影响范围。
- 测试方式和测试结果。
- 数据库、配置、接口、部署影响说明。
- 已知风险或不包含项。

PR 合并前检查：

- 关联 Issue 明确。
- 构建通过。
- 关键测试通过。
- 代码评审意见已处理或风险接受。
- 无敏感信息、账号、密钥提交。
- 如涉及数据库或配置，已提供回滚说明。

## 8. 迭代管理规则

每个迭代开始前，需要确认：

- 本轮包含的 Issue。
- 本轮排除的 Issue。
- 负责人和计划完成时间。
- 依赖项和风险项。
- 验收方式。

每个迭代结束前，需要确认：

- 已完成 Issue。
- 未完成 Issue 及原因。
- 新增缺陷和遗留风险。
- 可发布范围。
- 下一轮迭代建议。

## 9. 发布管理规则

发布前必须形成 `REL` 记录，至少包含：

- 版本号。
- 发布范围。
- 包含需求、缺陷、变更。
- 排除项。
- 已知问题。
- 数据库变更。
- 配置变更。
- 部署步骤。
- 回滚步骤。
- 发布负责人。
- 验证负责人。
- 发布窗口。
- 风险接受记录。

发布前检查必须覆盖：

- 分支和版本号已确认。
- 关联 Issue 和 PR 已完成检查。
- 测试结论已明确。
- 未关闭缺陷已评估。
- 数据库脚本和回滚脚本已准备。
- 配置项已确认。
- 部署步骤可执行。
- 回滚触发条件明确。
- 通知对象和应急通道明确。

## 10. Gitee 企业版 MCP 使用方式

Gitee 企业版 MCP 用于辅助研发过程管理，但关键结论必须由项目负责人、技术负责人或发布负责人确认。

可使用 MCP 完成：

- 查询企业、仓库、成员和项目。
- 查询 Issue、缺陷、变更和迭代范围。
- 查询 PR、PR diff、评论和合并状态。
- 汇总某个版本关联的 Issue 和 PR。
- 生成发布说明、变更清单和风险清单。
- 检查发布前未关闭 Issue、未合并 PR、未处理评论。
- 辅助生成客户可读的版本说明。
- 辅助分析客户变更影响范围。

推荐指令示例：

```text
用 Gitee MCP 查询本轮迭代的所有 Issue，并整理版本范围。
```

```text
读取 v1.2.0 相关 PR，生成发布说明和风险清单。
```

```text
检查 release/v1.2.0 发布前是否还有未关闭 Issue 或未合并 PR。
```

```text
根据这个客户变更，查询相关 Issue 和 PR，生成 CR 影响分析初稿。
```

## 11. 发布退出标准

版本发布阶段退出前必须满足：

- 发布范围已确认。
- 每个发布项都能关联需求、变更或缺陷。
- 发布前检查项完成率达到 100%。
- 回滚步骤已确认，必要时已演练。
- 发布验证结论明确。
- 已知问题已有处理计划或风险接受。
- 发布记录、验证记录和复盘建议已归档。

## 12. 例外处理

如规则不适用，必须记录：

- 例外事项。
- 例外原因。
- 影响范围。
- 风险说明。
- 批准人。
- 后续改进建议。

已基线化的需求、设计、代码、配置、数据库脚本和发布文档，后续修改必须走变更管理，不得静默覆盖。
